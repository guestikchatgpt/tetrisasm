# Как этот Tetris работает на уровне ассемблера

Этот файл — карта исходника `tetris.s`. Главный принцип: процессор не знает, что такое «фигура», «клавиша», «экран» или «очки». Для него существуют регистры, память, арифметика, сравнения и переходы. Всё остальное программа строит поверх них.

## 1. Откуда вообще начинается программа

В C обычно пишут `main()`, но до него уже выполняется runtime. Здесь runtime нет. ELF указывает Linux на символ `_start`, и ядро передаёт управление непосредственно туда.

Инструкция вроде:

```asm
mov rax, 60
xor edi, edi
syscall
```

означает не абстрактное «закрыть программу», а буквально: положить номер `exit` в `rax`, код возврата `0` в `rdi` и войти в ядро инструкцией `syscall`.

## 2. Почему стрелки нельзя просто прочитать как один символ

Обычный terminal находится в canonical mode: он собирает строку до Enter. Для игры это непригодно. `setup_terminal` через `ioctl(TCGETS/TCSETS)` меняет `termios`, отключая canonical input и echo.

Затем `fcntl` добавляет stdin флаг `O_NONBLOCK`, поэтому `read()` либо сразу отдаёт байт, либо немедленно сообщает, что данных сейчас нет.

Стрелки терминал кодирует ANSI-последовательностями:

```text
Up    = ESC [ A
Down  = ESC [ B
Right = ESC [ C
Left  = ESC [ D
```

Поэтому `process_input_byte` — маленький конечный автомат из трёх состояний.

## 3. Как представлено поле

Поле 10×20 — это просто 200 последовательных байт:

```text
board[0] ... board[9]      row 0
board[10] ... board[19]    row 1
...
board[190] ... board[199]  row 19
```

Адрес клетки `(x, y)` вычисляется формулой:

```text
index = y * 10 + x
```

`0` означает пустую клетку, `1` — зафиксированный блок.

## 4. Как представлена фигура

Каждый тетромино хранится как четыре пары локальных координат `(x, y)`. Для каждого типа заранее записаны четыре варианта поворота.

Например горизонтальный I:

```text
(0,1) (1,1) (2,1) (3,1)
```

Если сама фигура находится в `current_x=3`, `current_y=5`, то первый блок реально находится в `(3,6)`, второй в `(4,6)` и т. д.

Никаких объектов и структур языка высокого уровня здесь нет. Есть таблица байтов и арифметика адресов.

## 5. Collision detection

`can_place(x, y, rotation)` берёт четыре блока выбранного поворота и для каждого проверяет:

1. `absolute_x < 0` — нельзя;
2. `absolute_x >= 10` — нельзя;
3. `absolute_y >= 20` — нельзя;
4. соответствующий `board[index] != 0` — нельзя.

Если ни один из четырёх блоков не нарушил правила, функция возвращает `eax=1`.

И движение, и падение, и поворот используют одну и ту же проверку. Это важный архитектурный момент: вместо четырёх разных вариантов collision logic существует одна функция.

## 6. Как фигура падает

Главный цикл работает примерно каждые 20 мс. Само падение не обязано происходить каждый цикл.

`gravity_accum` накапливает миллисекунды. `get_gravity_interval` вычисляет интервал из уровня. Когда accumulator достигает этого значения, вызывается `gravity_step`.

`gravity_step` спрашивает `can_place` для `y+1`:

- можно — увеличивает `current_y`;
- нельзя — вызывает `lock_piece`.

## 7. Что делает lock_piece

`lock_piece` превращает временно падающую фигуру в постоянную часть поля: вычисляет четыре абсолютных адреса и записывает в `board` единицы.

После этого вызывается `clear_lines`.

## 8. Как удаляется заполненная линия

`clear_lines` идёт снизу вверх и проверяет все 10 байт строки.

Если все ненулевые, строка полная. Тогда каждая строка выше копируется на одну позицию вниз, а верхняя строка заполняется нулями.

В языках высокого уровня это выглядело бы как массивы и циклы. Здесь те же циклы выражены через `cmp`, условные `j*` и изменение регистров-счётчиков.

## 9. Очки и уровни

После `clear_lines` число удалённых строк индексирует таблицу:

```text
0 -> 0
1 -> 100
2 -> 300
3 -> 500
4 -> 800
```

Полученное число умножается на текущий level.

Новый level вычисляется целочисленным делением:

```text
level = lines_total / 10 + 1
```

Инструкция `div` возвращает quotient и remainder аппаратно.

## 10. Как рисуется экран без графической библиотеки

Весь экран текстовый. Одна занятая клетка — строка `[]`, пустая — два пробела.

`render` не делает `write()` для каждой клетки. Это было бы 200+ переходов в kernel на один кадр. Вместо этого программа складывает весь кадр в `render_buffer`, а затем делает один большой `write(1, buffer, length)`.

ANSI `ESC[H` возвращает cursor в начало экрана, поэтому следующий кадр перезаписывает предыдущий.

## 11. Откуда берутся случайные фигуры

`clock_gettime` даёт seed. Затем работает `xorshift32`:

```text
x ^= x << 13
x ^= x >> 17
x ^= x << 5
```

После этого остаток от деления на 7 даёт число 0..6 — индекс одной из семи фигур.

Это хороший пример того, насколько прямо ассемблер показывает реальные операции CPU: shifts и XOR здесь не скрыты за библиотекой генерации случайных чисел.

## 12. Что делает linker

Assembler (`as`) знает, как перевести отдельные инструкции в машинный код, но финальные адреса секций и символов ещё не определены. Он создаёт `tetris.o` с секциями `.text`, `.rodata`, `.bss` и relocation records.

`ld` собирает их в один ELF executable и назначает реальные virtual addresses.

При старте Linux отображает эти сегменты в память процесса, выставляет stack и instruction pointer на `_start` — после чего начинает исполняться первая инструкция нашего кода.

## 13. Как изучать практически

Полезный следующий этап после чтения комментариев — смотреть, что получилось после сборки:

```bash
make
objdump -d -Mintel build/tetris | less
readelf -h build/tetris
readelf -S build/tetris
strace ./build/tetris
```

`objdump` показывает реальные инструкции в ELF, `readelf` — его структуру, а `strace` особенно наглядно показывает границу между кодом программы и ядром Linux: `ioctl`, `fcntl`, `read`, `write`, `nanosleep`.
